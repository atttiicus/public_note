## Node.js

前端工程化的基础是 Node.js。

JavaScript 代码在浏览器中由 V8 引擎执行。Node.js 将 V8 引擎带到了浏览器之外，使 JavaScript 可以在本地环境运行——无论是构建工具、脚手架，还是后端服务，都依赖这一能力。

## 包管理工具：npm、yarn、pnpm

有了 Node.js，还需要一套机制来引入和管理第三方依赖库。类比 Python 的 pip、Rust 的 Cargo，Node.js 生态中有三个主流包管理器。

### npm

Node.js 官方内置的包管理工具，兼容性最广。早期版本速度较慢，后续版本已有显著改善。

### yarn

Facebook 推出，用于解决早期 npm 的速度与依赖一致性问题。

- **v1**：用法与 npm 相近，速度更快，锁文件机制更可靠，但仍依赖 `node_modules` 目录。
- **v2+（Berry）**：引入 PnP（Plug'n'Play）模式，用压缩包替代 `node_modules`，彻底规避了巨型目录问题。

v1 已停止更新，最新版本停留在 `1.22.22`；当前最新大版本为 v4。但经实际测试，yarn v4 与部分现有项目（尤其是 Vite + Vue 项目）的兼容性较差，存在较多运行错误。

### pnpm

后起之秀，通过硬链接机制共享依赖，节省磁盘空间，在 monorepo 多包项目中优势尤为突出。

> 三者均能完成「安装依赖、锁定版本、清理缓存」等基础任务，选型时主要考虑团队习惯与项目结构。

## 构建工具：Vite、Webpack

**构建**的核心职责：将源码（TypeScript、Vue SFC、JSX、CSS 预处理器、图片等）转换为浏览器可高效执行的产物，并在开发期提供快速反馈（热更新/HMR）。

Vite 和 Webpack 均承担「开发体验 + 产物输出」两项职责，但设计理念不同。

### Webpack（老牌全家桶）

- **思路**：一切资源皆模块，先分析完整依赖图，再整体打包（bundle）后交给浏览器。
- **优点**：生态成熟，loader/plugin 几乎覆盖所有需求；历史兼容性强；支持深度自定义。
- **缺点**：初次构建与增量重构建速度较慢；配置项繁多，上手门槛高。

### Vite（开发体验优先）

- **开发阶段**：利用浏览器原生 ESM 按需加载源码，仅对非原生语法（TypeScript、Vue、JSX）做即时转换，底层使用 esbuild（Go 实现，速度极快）。
- **构建阶段**：交由 Rollup 完成优化（tree-shaking、代码分割、压缩）。

Vite 本质上是一个编排层：Dev Server（esbuild 预处理）+ Rollup 打包的组合。

- **优点**：启动秒级完成，HMR 响应迅速；默认配置即可满足大多数场景；对现代语法与框架支持良好。
- **缺点**：极端或历史复杂场景下的深度定制能力仍不及 Webpack 生态；部分旧式脚本需要额外兼容处理。

:::color5
一句话总结：Webpack 是「先打好包再服务」；Vite 是「先以原生 ESM 服务，最终再打包」。

新项目追求开发体验 → Vite；遗留项目或复杂构建链条 → Webpack。

_（注：通常将 Vite/Webpack 称为「构建工具」，将底层的 esbuild/Rollup 称为「打包工具」，下节分开介绍。）_
:::

## 打包工具：esbuild、Rollup、Webpack

**打包**聚焦于：解析依赖图 → 合并/拆分模块 → 优化（tree-shaking/压缩）→ 输出可部署的 bundle/chunk。

### esbuild

- **特点**：Go 实现，多线程 + 流式处理，速度远超同类工具（数量级差距）。
- **适用场景**：开发期依赖预构建、脚手架、内部工具、追求极致构建速度的任务。
- **不足**：高级代码分割策略和复杂插件生态不及 Rollup/Webpack。

### Rollup

- **特长**：面向 ESM，tree-shaking 精细，输出产物干净，适合开发库（支持输出 ESM/CJS/UMD 多格式）。
- **不足**：构建复杂应用需要拼装大量插件，不如 Webpack 开箱即用。

### Webpack

既承担打包职责，也内置 Dev Server；资源类型覆盖广，历史方案兼容能力强，在大型单页应用、多入口项目和旧代码迁移场景中仍有重要价值。

**典型组合：**

- Vite（开发）→ Rollup（构建），内部用 esbuild 预构建依赖并转换 TypeScript
- 纯 esbuild：快速产出临时或内部工具包
- 纯 Webpack：贯穿全流程的传统方案

:::color5
速记：

- esbuild → 极速
- Rollup → 做库 / 极致 tree-shaking
- Webpack → 大而全
- Vite → 体验编排层（调度 esbuild + Rollup）
:::

## UI 框架：Vue、React、Angular

三者都用于构建用户界面，但设计哲学差异显著。

### Vue（渐进式框架）

可以仅作为视图层使用，也可逐步引入路由、状态管理、构建工具，组成完整的「全家桶」。单文件组件（SFC）结合 Proxy 驱动的响应式系统（Vue 3），语法直观，上手快。适合中小到中大型业务的快速开发。

### React（UI 库）

专注于 state → UI 的映射，路由、状态管理、数据请求方案均由生态自由组合。函数式 + Hooks 的编程模型灵活度高，但也更容易引入过度抽象或性能陷阱。适合需要高度定制、跨端（React Native/Electron）或基建成熟的团队。

### Angular（企业级框架）

内置依赖注入、路由、表单、HTTP 客户端、CLI 及严格的项目结构，与 TypeScript 深度绑定。概念体系较重（Module/Component/Service/DI/RxJS），学习成本高，但换来架构统一与长期可维护性。适合大型后台系统和需要统一规范的团队。

一句话：快速上手 → Vue；按需灵活组合 → React；自带完整架构 → Angular。

Svelte、Solid、Qwik 等新一代框架值得关注，但建议先将主流三件套吃透。

## 模块化规范：ESM、CommonJS、AMD

前端存在多种模块规范，根源在于历史演进：浏览器最初没有模块机制，社区各自补位（AMD）；Node.js 为服务端场景设计了同步加载方案（CommonJS）；最终 ECMAScript 标准委员会推出了官方模块规范（ESM）。

### CommonJS（CJS）

```js
const a = require('a')
module.exports = { ... }
```

同步加载，适合服务端文件系统。导出的是对象引用，修改导出对象的属性对后续 `require` 可见。Node.js 旧项目中大量使用，目前仍被广泛支持。

### AMD

```js
define(['dep'], function(dep) { return api })
```

面向浏览器的异步加载方案，解决网络延迟导致的阻塞问题。代表实现为 RequireJS。现代新项目基本不再直接使用。

### ESM（ECMAScript Module）

```js
import { x } from './x.js'
export default { ... }
```

静态可分析（便于构建工具做 tree-shaking），浏览器原生支持 `<script type="module">`，导出为实时绑定（live binding）。

**补充说明：**

- **UMD**：打包层面同时兼容 CJS、AMD 和全局变量，常见于发布供他人使用的库。
- **IIFE**：早期用立即执行函数隔离作用域的"伪模块"方案。
- **互操作**：ESM 导入 CJS 得到默认导出的整个模块对象；CJS `require` ESM 受 Node.js 版本和 `package.json` 中 `"type"` 字段约束；打包工具负责处理大量兼容性转换。
- Node.js 通过 `"type": "module"` 字段或 `.mjs`/`.cjs` 文件后缀区分模块类型。

**心智模型**：CJS = Node.js 旧世界；AMD = 浏览器历史方案；ESM = 现在与未来。理解历史背景后，新代码应直接使用 ESM。

打包工具的核心价值之一，正是将多种模块来源统一转换为浏览器可高效加载的最终形式。

## 为什么前端看起来如此"杂乱"

一个「写页面」的工作，为何衍生出三套包管理器、四五种构建工具、多个框架和若干模块规范？可以从以下几个层面理解：

**1. 历史包袱的叠加演进**

浏览器最初几乎不提供工程化支持，社区缺什么补什么。旧方案不能立即废弃（项目还在跑），新旧方案因此并存（CommonJS 与 ESM、Webpack 与 Vite、npm 与 yarn/pnpm）。

**2. 运行环境碎片化**

目标环境不只是最新版 Chrome，还包括旧浏览器、Node.js、SSR、Edge Runtime、Electron、微信小程序、各种嵌入式 WebView。不同环境的限制各异，催生了大量 polyfill、转译和适配工具。

**3. 语言标准化相对滞后**

JS 规范演进节奏慢于实战需求。社区先造（CoffeeScript、Babel、TypeScript、各种模块格式），标准委员会再逐步吸收（class、ESM、可选链）。过渡期必然形成"并存 + 迁移"的局面。

**4. 性能与开发体验的军备竞赛**

不同工具在不同维度极致优化：esbuild 拼速度，Rollup 拼输出洁净，Webpack 拼全能，Vite 拼秒启动。竞争导致分化，但也推动了整体进步。

**5. 生态开放与低进入门槛**

JavaScript 进入门槛低，全球开发者众多，迭代快；"不满意就造轮子"的文化通过 npm 得以快速传播，进一步加速了生态分化。

**6. 需求边界持续扩张**

前端职责从"写页面"延伸到 SSR/SSG（Next.js/Nuxt）、同构渲染、边缘渲染、实时协作、WebGL/WebGPU、跨端（React Native/Tauri）、微前端、低代码等。每出现一个新场景，就会诞生一批专用术语和新工具。

**7. 商业与社区驱动并存**

大厂（Meta、Google、阿里、字节、微软）将内部解决方案开源推广（React、Angular、Rspack、Turbopack 等），自带流量，促使多路线并行发展。

**8. 迁移成本制约新工具普及**

工具迁移不只是功能对比，还需评估构建脚本、插件生态、CI 配置、团队认知和潜在 Bug 风险。旧工具因此不会迅速消亡，形成"代际共存"。

:::color5
一句话概括：前端是「需求急速膨胀 + 标准化相对滞后 + 进入门槛低 + 多运行时并存 + 旧项目存量庞大」交叉作用的结果。
:::

## 如何在杂乱中保持清晰

1. **先抓恒定核心**：HTML/CSS/JS 基础、HTTP 协议、浏览器运行机制（事件循环、渲染、缓存、网络）。
2. **再选一条主线**：例如 Vue + Vite 或 React + Vite/Next.js，完整交付一个项目。
3. **遇到陌生名词先分类**：判断它属于「语法/标准、运行时、框架、构建层、打包层、部署层、性能优化手段、工程组织模型」中的哪一类。
4. **定期低频巡检**：每隔 3~6 个月了解生态是否出现范式级变化（如 Server Components、Edge Functions、WebGPU）。
5. **避免工具驱动学习**：带着真实问题选工具，而不是「听说很火先全装一遍」。

**最后的心态**：工具会淘汰，但底层原理（模块划分、依赖图、编译与打包、资源加载、渲染与状态管理、缓存策略）的迁移性很高。把注意力放在「为什么需要它」而不是「API 细枝末节」上，焦虑感会下降很多。

本文的核心脉络：运行时（浏览器/Node.js）→ 模块与依赖 → 打包/构建链 → 框架（UI 与状态）→ 交付与性能 → 生态演化。理解这条链条之后，再遇到新术语，只需定位它处于链条的哪一段即可。
